## Limitations

- **No confirm step.** Remove and Revoke act on one click, because the plan asks for a confirm only on Documents delete. Add one if accidental revokes are a concern.
- **No "created by" column** in pending invites. The contract returns a user id, not an email; showing the creator would mean joining it against the members list.
- **No revoke for invites.** The HTTP contract has no route to cancel a pending invite.
- **Possible double load in dev.** If the app runs under React StrictMode, development fires each list GET twice. Production does not.

## Findings outside the owned files

- **`frontend/src/App.test.tsx`, the cause of the red `check:frontend`.** `respondWith` answers every fetch with one body. Now that Settings loads `GET members`, `invites` and `api-keys`, the owner-settings test gets a `Me` object where it expects an array, and the render throws. The fix I used to prove this (owner: the main session; it is 5.2's file):
  ```ts
  const fetchMock = vi.fn(async (url: string) => new Response(JSON.stringify(status !== 200 || url === "/api/me" ? body : []), { status, headers: { "Content-Type": "application/json" } }));
  ```
  - **Effect on 5.3:** the same fixture will likely break 5.3 too. "/ opens the first workspace" renders Documents, which will call `GET documents`. This one fix covers both.
- **`api.ts`** casts response bodies with `as T` and never checks their shape. That is fine against our own server, but it's why a bad fixture surfaces as a crash rather than an error message. No change needed for v1; this is just a note.
