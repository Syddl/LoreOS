## Limitations

- The screen hasn't been checked visually or in a real browser (layout, the dialog, focus moving through the picker and dialog). That needs the manual screenshot row `check:frontend` already lists.
- The picker has no `accept` list or file-type hint. The allowed extensions belong to the backend (`parsing.KINDS`), so copying them here would make a second owner. The 415 detail names the allowed types.
- A 404 on delete (the document is already gone) shows its detail and doesn't remove the row.
- Status changes from polling aren't announced to screen readers; there is no live region.
- If a poll fails with anything other than a 401, the error shows above the list. Polling keeps going while documents are unsettled and clears the error on the next successful poll.

## Findings outside the owned files

- **`frontend/src/App.test.tsx`** (owner: 5.2 / main session) is the blocker. `respondWith` sends the same body to every fetch, so Documents gets `Me` for `GET documents`. This is the fix I tested:
  ```ts
  const fetchMock = vi.fn(async (url: string) =>
    new Response(JSON.stringify(url.endsWith("/documents") ? [] : body), { status, headers: { "Content-Type": "application/json" } }),
  );
  ```
  Expect the same failure from 5.5: the third App test renders Settings, whose member, invite and key lists will also receive `Me`. Routing the mock by URL in one place covers both.
- **Note for 5.4 and 5.5:** after `user.upload`, jsdom's own form handling still sees the file input as empty. That means `required` blocks the submit and `new FormData(form)` holds no file. Read `input.files` directly; that's why this screen uploads on the picker's change event instead of through a form submit.
