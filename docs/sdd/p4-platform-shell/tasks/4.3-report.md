How the IDOR guard works:
- The members, invites and keys routes take `member: Owner`, where `Owner = Annotated[Member, Depends(require_owner)]`. `require_owner` depends on `current_member`, which reads the path's `workspace_id`.
- Every statement on `memberships`, `invites` or `api_keys` binds `:w = member.workspace_id`, so an id from another workspace matches no row and gets 404.
- The workspace list and create routes use `current_user`, so a key gets 403 there.

## Old vs new

| Behaviour | Before | After |
|---|---|---|
| `GET /api/workspaces` | 404 | The user's `[{id, name, role}]`, ordered by `created_at`. `eval-%` names are filtered out even when the user has a membership there. |
| `POST /api/workspaces {name}` | 405 | 201 `{id, name, role: "owner"}` plus an owner membership. A name that is blank after trimming, over 100 characters, or starts with `eval-` gets 422. |
| `GET members` | 404 | `[{user_id, email, role}]`, owner only |
| `DELETE members/{user_id}` | 405 | Locks the owner rows (`select ... for update`), then runs `delete ... where workspace_id = :w and user_id = :u returning role`. No row gets 404. Deleting the last owner gets 409, and raising rolls the delete back. |
| `POST invites` | 405 | 201 `{token, expires_at}`. The token is `token_urlsafe(32)`, stored as `auth._sha256(token)`, with `created_by` set and an expiry 7 days out. |
| `GET invites` | 404 | `[{created_at, expires_at, created_by}]`, unused and unexpired only |
| `POST api-keys {name}` | 405 | 201 `{id, name, prefix, key, created_at}` via `auth.create_key`. The prefix and `created_at` are read back from the stored row. |
| `GET api-keys` | 404 | `[{id, name, prefix, created_at, last_used_at, revoked_at}]`, never the key |
| `DELETE api-keys/{key_id}` | 405 | `set revoked_at = coalesce(revoked_at, now()) where id = :id and workspace_id = :w`, then 204. No row gets 404. Revoking twice gets 204 and keeps the first `revoked_at`. |

**How the race test works:** a third transaction holds the owner rows `for update`. It fires both DELETEs through an `httpx2` ASGI client, waits until `pg_stat_activity` shows 2 backends waiting on a lock, then commits. That makes it deterministic: with the route's lock the outcome is `[204, 409]` with one owner left; without it, both requests count 2 owners and the outcome is `[204, 204]` with none left.

## Limitations

- **Stale authorization:** `current_member` runs in its own transaction before the route does. An owner who is removed while their request is in flight can still finish that one request. In the race, the loser gets 409 because of the count, not because it lost ownership. This is the same across every route in this codebase. A fix in this route would be to re-check `member.user_id` against the locked owner rows (2 lines); I left it out to match the contract's `204 | 409`.
- **Reserved `eval-` names:** refusing `eval-` names with 422 goes beyond the contract. Without it, a workspace created with that name would vanish from its creator's list.
- **No invite revoke:** invites have no id in the contract, so an owner cannot revoke one.
