## Old vs new

| Behaviour | Before | After |
|---|---|---|
| `python -m loreos.admin reset-password <email>` | No module | Asks twice with `getpass`. The email is normalized with `auth.normalize_email`. In one transaction it runs `update ... returning id`, then deletes all of that user's sessions. On success it prints the email and how many sessions it ended, and exits 0 |
| The two entries differ | n/a | Exits 1 with "the two passwords differ; run the command again and type the same one twice" |
| `password_problem` reports something | n/a | Exits 1 with "the password needs at least 12 characters; run the command again" |
| Unknown email | n/a | Exits 1 with "no user has the email <email>; check the spelling". The update matched no row, so nothing changes |
| `DATABASE_URL` unset or wrong | n/a | Exits 1 with the `RuntimeError` text from settings, which names the fix (same handling as `verify_rls`) |
| Wrong arguments | n/a | Prints `USAGE` and exits 2, before any prompt |

The password is hashed before the transaction opens, so no transaction is held open while argon2 runs or while the command waits at a prompt.

## Limitations

- **The session count in the success message is not checked.** Under the mutation the command still printed "ended 2 sessions", because a `select` reports a row count too. The database assertion is what catches the skipped delete. An assertion on "ended 2 sessions" in stdout would close this gap.
- **The email is checked last.** An unknown email is found only after the operator has typed the password twice and it has been hashed. Checking the email before the prompts would need a second session, and the brief asks for one.
- **No end-to-end run against a real terminal.** The interactive path through `python -m` was not run against a live user, because `getpass` cannot be patched from outside the process. `main()` is exercised directly.
