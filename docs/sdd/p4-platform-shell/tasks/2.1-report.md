## Old vs new

| Behaviour | Before | After |
|---|---|---|
| Counting calls per bucket | No module. | One upsert, `insert ... on conflict (bucket, window_start) do update set count = rate_limits.count + 1 returning count`, in fixed windows of `window_s` counted from the epoch. A call is allowed while `count <= limit`. |
| `retry_after` | n/a | 0 when allowed. When refused, `ceil(window end - now)`, so it is always 1 to `window_s` and never 0. |
| Refund | n/a | `count = greatest(count - 1, 0)` on the row for `(bucket, window_start)`. A refund that arrives after the boundary still goes to the window the call was counted in. |
| Old windows | n/a | Never pruned. The `ponytail:` comment says the table grows by one row per bucket per window, and to delete rows older than the longest window when its size matters. |

How each case in plan.md 2.1 is covered:
- **3 allowed, the 4th refused:** at T0+20.5 s the results are `[True, True, True, False]`. `retry_after` is exactly `[0, 0, 0, 40]`, which checks both the 1 to 60 range and the rounding up.
- **Refund:** after 3 calls, a refund lets a 4th call through and refuses the 5th.
- **Refund on an empty bucket:** one call and then two refunds leave the count at 0, not -1. After that, 3 calls are allowed and the 4th is refused, so the floor actually matters.
- **Window boundary:** a call at 59 s, then a call at 61 s, then a refund of the first slot. The rows end as `[(T0, 0), (T0+60s, 1)]`.
- **Next window:** after a refusal, moving the clock to T0+60 s allows a call, with the new `window_start`.
- **Concurrency:** 10 calls through `asyncio.gather` with limit 5. NullPool gives each call its own connection. The row's count is exactly 10 and exactly 5 calls are allowed.
- **Buckets:** bucket `a` is exhausted at limit 1 and bucket `c` is still allowed.

## Limitations

- Windows line up with the Unix epoch, not with each bucket's first call. With the 15-minute login window, a burst that straddles a boundary can get up to twice the limit through. This is how fixed windows work, and the plan chose them.
- A refund for a `(bucket, window_start)` with no row does nothing and creates no row. No test checks this directly. The floor is tested on a row that exists.
- Nothing prunes the table. The `ponytail:` comment names the ceiling, and 6.2 owns the KNOWN-GAPS row.
