## Old vs new

| Behaviour | Before | After |
|---|---|---|
| Storing an upload | Only `ingest()`, which stores and processes inline | `enqueue()` stores a `pending` row and embeds nothing. `kind_of` runs first. A duplicate that has not failed comes back unchanged. A `failed` duplicate goes back to `pending` with `attempts` 0 and `error`, `next_attempt_at` and `locked_until` cleared |
| Storing a URL | none | `enqueue_url()` normalises the URL (a `Refused` propagates) and uses the sha256 of the normalised URL. A new URL stores a `url` row with `filename` and `source_url` set to the URL and no content. An existing row of any status is re-queued as above, under `set local lock_timeout = '2s'`, so a row the worker holds raises `55P03` after about 2 s |
| Processing | `process()` set `processing`, added 1 to `attempts` and deleted the chunks before parsing | `run_stages()` takes `select ... for update` first. For a `url` row it fetches (stage `fetch`) and parses with `kind=fetched.kind`. Then it chunks, embeds, replaces the chunks and marks `processed` with `processed_at`, clearing `error`, `next_attempt_at` and `locked_until`. It returns the chunk count. A failure raises `StageError(stage)` from its cause, and nothing is written before the store stage |
| Fetched bytes | none | Stored in `content` in the same final update, with `coalesce(:c, content)`, so an upload's bytes are never sent back to the database |
| `process()` failure | `failed` with the error, `attempts` already +1 | Wraps `run_stages` in a savepoint. On `StageError` it calls `record_failed` with P1's text `<stage>: <Exception>: <message>`. `record_failed` sets `failed`, adds 1 to `attempts`, deletes the chunks and runs the error through `scrub` |
| `attempts` | +1 on every run | A success never adds to it. A processed document has 0, a failed rerun has 1 |
| `ingest()` | — | Same signature: `enqueue`, then `process` if the row is `pending`. A processed or `processing` duplicate is returned as stored; a `pending` duplicate is processed inline, so the evaluation never gets a `pending` row back |

## Limitations

- **`lock_timeout` lasts the whole session.** It applies to every later statement in the caller's session, not just the re-queue, and 4.4's route should know that. Scoping it more tightly would need a `set_config` call, which the isolation scan forbids outside `db.py`.
- **Not run: the cancelled-session cleanup on the red path.** If mutation 2 is applied, `wait_for` cancels a session while it waits on the lock. I expect asyncpg's cancel and NullPool's close to release the holder's lock, so later tests do not hang, but I have not seen it happen.
- **Only file re-queues skip the lock timeout.** A failed upload's re-queue in `enqueue` runs without `lock_timeout`, as the plan scopes it. The worker's claim never takes a `failed` row, so the risk is low.
- **A file and a URL can share a hash.** A `.txt` file whose bytes are exactly a normalised URL has the same sha256 as that URL, so the two would collide on `unique (workspace_id, sha256)`. Not handled.
- **`record_failed` leaves the worker's columns as they are.** It does not clear `locked_until` or `next_attempt_at`, as the contract specifies. 3.3's fenced writes may want their own SQL.

## Findings outside the owned files

- **STATUS / plan contract (main session):** `ingest()` now processes a `pending` duplicate inline instead of returning it unchanged. It keeps the evaluation's "processed on return" contract when the worker queued the same bytes first. Worth a line in the 3.1 handoff row.
- **3.3 (worker):** `run_stages` returns the chunk count but does not log. The worker logs it and writes its own `<stage>: <class>: ...` text, calling `scrub` itself unless it routes through `record_failed`, which already scrubs.
