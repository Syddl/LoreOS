## Old vs new

| Behaviour | Before | After |
|---|---|---|
| Password hashing | none | `argon2.PasswordHasher()` with its defaults (argon2id). `MIN_PASSWORD = 12`, and `password_problem` names 12. `verify_password` returns False on a mismatch and on a hash it cannot read. |
| Unknown email at login | n/a | `authenticate` checks a cached dummy hash, so an unknown email and a wrong password each run exactly one verification, through `async _verify` (`asyncio.to_thread`) |
| Session tokens and keys | n/a | Both come from `token_urlsafe(32)` and are stored only as sha256 hex. A key is `lo_sk_` plus the token; `prefix` is the first 8 characters of the random part, and the hash covers the whole `lo_sk_...` string. Sessions expire 14 days after creation, using the database clock (`now() + make_interval(days => 14)`). |
| `current_member` | n/a | Any `Authorization` header decides alone: not `Bearer lo_sk_...`, unknown or revoked gives 401; another workspace's key gives 404 and does not update `last_used_at`; a valid key updates `last_used_at` and gets role `member`. Without that header the cookie decides: no session or an expired one gives 401, no membership gives 404. Neither credential gives 401. |
| `require_owner` / `current_user` | n/a | `require_owner` gives 403 to a member and to a key. `current_user` reads the cookie only: 403 when an `Authorization` header is present, 401 without a session. |
| Cookie | n/a | `loreos_session` is `HttpOnly`, `SameSite=lax`, `Path=/` with `Max-Age=1209600`, and `Secure` only when `request.url.scheme == "https"`. `clear_session_cookie` sets `Max-Age=0`. |

Every name and signature in the 2.2 row of the handoff contracts exists as written. `create_user` hashes off the event loop too.

What the cases cover, against plan 2.2:
- **Passwords:** the hash is argon2id and verifies; an 11-character password is refused naming 12; an email is stripped and lowercased; `authenticate` finds a user by the normalised email.
- **Dummy hash:** a spy on `argon2.PasswordHasher.verify` counts exactly one call for an unknown email and one for a wrong password, and both return None. The spy patches the class because `PasswordHasher` uses `__slots__`.
- **Storage:** the stored session id and key hash equal the sha256 of the token, and neither row contains the token or the key's random part. A session expires after 14 days, an expired session finds no user, and `delete_session` ends it.
- **Key format:** `lo_sk_[A-Za-z0-9_-]{43}`, with a prefix of 8 characters from the random part.
- **`current_member`:** every outcome in the plan, plus an unknown or expired cookie and `last_used_at` before and after use. The bad-header-with-good-cookie case is parametrised over an unknown key, `Bearer not-a-key`, `Bearer ` with no key, a `Basic` header and an empty header.
- **`require_owner`:** an owner gets 200, a member 403, a key 403.
- **`current_user`:** no cookie gives 401; a cookie gives the user; a valid key sent together with a valid cookie gives 403.
- **Cookie:** the flags are checked over http and https, plus clearing.

What these checks do not exercise:
- Timing: the tests count `verify` calls and do not measure time.
- Concurrency at the `_verify` seam (4.2's test).
- The real routes and the Origin middleware.

## Limitations

- **A choice beyond the brief:** any `Authorization` header, not only a Bearer one, sends the request down the key path, so it never falls back to the cookie and fails closed. A `Basic` header with a valid cookie gets 401, and `current_user` answers 403 to any `Authorization` header. This is stricter than "a Bearer header decides alone" and is consistent with an Origin exemption for Bearer requests only.
- **No password-length guard in `create_user` or `hash_password`.** The routes in 4.2 and the admin reset in 3.2 must call `password_problem` themselves. The docstring of `create_user` says so.
- **The dummy hash is computed on the first unknown-email login,** not at import. That one login costs an extra hash, once per process. Computing it at import would close this if it matters.
- **Expired sessions are never deleted from the table;** they are only refused. Nothing asked for pruning.
- **Not tested:** the sha256 lookup on a key with the right prefix but a wrong body is covered only as "unknown key gives 401", with no timing assertion. That is acceptable because the comparison is a hash lookup, not a string compare.

## Findings outside the owned files

- `routes/auth.py` and the Origin middleware (owner 4.1/4.2): the Origin exemption has to cover only requests that `current_member` authenticates by key alone. Exempting requests whose `Authorization` starts with `Bearer` is safe, because `current_member` sends every request with an `Authorization` header to the key path. A wider exemption, such as any `Authorization` header, would also be safe. Exempting a request that `current_member` then authenticates by cookie would not.
- None otherwise. The source scans in `test_isolation.py` already allowlist `auth.py`, and the full backend run shows they pass.
