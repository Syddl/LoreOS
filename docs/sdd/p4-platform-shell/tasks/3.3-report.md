## Old vs new

| Behaviour | Before | After |
|---|---|---|
| Queued documents | nothing processes them | **Claim:** one `for update skip locked` statement in `system_session` takes the oldest due `pending` row, or a `processing` row whose lease ran out. **Processing:** the claimed row gets a 10-minute lease and is processed in the document's `workspace_session`, with `set local idle_in_transaction_session_timeout = '600s'`, which shows as `10min` |
| Expired lease | none | Adds 1 to `attempts` and writes `lease: transient: the worker stopped before finishing (lease expired)`. At the third count the row becomes `failed` and its chunks are deleted, without processing; `run_once` returns `transient` |
| Failure record | none | Written in a new `system_session`, only `where id = :d and workspace_id = :w and locked_until = :claimed_lease`. The error text is `<stage>: <class>: <Exception>: <message>`, passed through `scrub`. If no row is updated, the worker logs `worker lost document=<id>: ...` and does not raise |
| Permanent / transient / systemic | none | **Permanent:** `failed`, `attempts` +1. **Transient:** `pending`, retried after 30 s and then 120 s, `failed` at the third attempt. **Systemic:** `pending`, not counted, and the loop pauses 300 s. A move to `failed` always deletes the chunks |
| Stop | none | A `CancelledError` or `KeyboardInterrupt` releases the claim (`pending`, lease cleared, not counted) and re-raises. On Linux, SIGTERM cancels the main task, so it releases the same way |
| Startup | none | Checks `settings.startup_problems()`, then `verify_rls.problems()`. Each problem is printed as `worker: <problem>` on stderr, and the worker exits 1 |
| Loop | none | Polls every 2 s while idle. After `systemic` it logs `worker paused class=systemic seconds=300` and sleeps. A database error (`SQLAlchemyError` or `OSError`) during a claim or a record is logged, then it sleeps 2 s and carries on |
| Wrong embedding size | `ValueError` after every batch had been paid for | `EmbeddingDimensionError` after the first batch |

All four log lines from the contract are emitted. The `failed` line is also written for a counted lease expiry, with `stage=lease class=transient`.

Two calls of my own that the plan does not state:
- **Systemic retry time.** A systemic failure sets `next_attempt_at` to now + 300 s. Without it the row is due again at once, so `drain()` would loop forever, and the pause is the worker's own anyway.
- **Stage name outside `run_stages`.** A failure that is not a `StageError` (the lock select, the session setup, the commit) is recorded with stage `store`.

The cases cover every one plan.md 3.3 lists:
- **Transient** (`APITimeoutError`): `attempts` 1, then 2, retried at about +30 s and then +120 s, with the old chunks kept meanwhile. At 3 the row is `failed`, `error` starts `embed: transient: APITimeoutError: `, and no chunks are left.
- **Permanent** (a scanned PDF): `failed`, 1, with the exact error text, and `fake_embed` receives nothing.
- **Systemic** (`AuthenticationError`, and `RateLimitError` with `insufficient_quota`): `pending`, 0, and `run_once` returns `systemic`.
- **The loop:** it sleeps 300 after systemic, 2 when idle, none after a processed document, and 2 after an `OperationalError`, with both log lines.
- **Classification:** 28 parametrised rows, one per table entry.
- **Claims:** two concurrent claims give one job. With `LEASE` at 0, a row paused inside `fake_embed` is not taken by a second claim, and the test confirms its lease had already run out.
- **Lease:** an expired lease is counted once, then processed (`processed`, 1). At `attempts` 2 it ends `failed` with the lease error, no chunks, and no embedding call.
- **One transaction:** a wrong-sized second vector gives `pending`, 1, `store: transient: `, and the previous chunks are kept.
- **Killed midway** (a custom `BaseException`): the row stays `processing`. After the lease expires it ends `processed`, 1, with exactly the earlier chunks.
- **Stopped:** both `CancelledError` and `KeyboardInterrupt` leave the row `pending`, 0, with no error and no lease.
- **Fence:** a stale record and release change the row not at all, it stays `processing` under the fresh lease, and two `lost` lines are logged.
- **Processing context:** inside `fake_embed`, the session reads `('10min', 'loreos_app', <the document's own non-default workspace>)`.
- **Startup:** a blank key exits 1 naming `OPENAI_API_KEY is not set`, and a `verify_rls` problem exits 1 naming it; the loop never starts in either. A positive case starts it.
- **Dimension:** with `EMBED_BATCH` at 2 and 3 inputs, there is exactly one API call, then `EmbeddingDimensionError`.

What the cases do not exercise:
- a real SIGTERM, or a real task cancel through `asyncio.run`;
- a real lost database connection;
- a real OpenAI error response (the errors are built in the test);
- `main()` running the loop for real.

## Limitations

- **Unreachable database at startup:** if the database cannot be reached during the `verify_rls` check, the worker exits with a traceback, not a `worker:` line. Settings problems are reported first, without touching the database.
- **Cancelled during a claim or record:** a stop that lands inside `claim()` or `record_failure()` releases nothing. The lease recovers the row after 10 minutes, and that recovery counts as one attempt.
- **Database down while recording:** if the database is lost while recording a failure, the row stays `processing` until its lease runs out, then counts as an expiry.
- **Idle timeout tied to `LEASE`:** the timeout is built from `LEASE` so the value has one owner. A test that sets `LEASE` to 0 therefore also turns the timeout off; that is harmless.
