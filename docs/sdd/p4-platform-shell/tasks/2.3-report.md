## Limitations

- **HTML speed:** a flat 4.8 MB page took about 9.4 s to parse in a one-off probe. bs4's own `html.parser` accounted for 7.7 s; the section walk is linear (about 0.8 s). The plan chooses `html.parser`, so a page near the 5 MB fetch limit costs the worker roughly 10 s.
- **HTML word joins:** text pieces are joined with a space, so a word split by inline markup (`Hel<b>lo</b>`) reads as two words. This is marked with a `ponytail:` comment.
- **HTML `<title>`:** it is not in the drop list, so its text lands in the leading section with an empty path. Neither the spec nor the tests pin this.
- **DOCX:** text in content controls, text boxes, headers and footers is not read, because `iter_inner_content` yields only body paragraphs and tables. A vertically merged cell's text repeats on each row it spans.
- **Empty headings** in both formats are treated as body text and do not enter the path. The Markdown parser would push an empty title.
- **Evaluation key:** `parsing.py` is in the evaluation key (`run.KEYED_SOURCES`), so this change gives the evaluation workspace a new name. `parse_docx.py` and `parse_html.py` are not keyed; that is harmless while the evaluation corpus has no DOCX or HTML.
