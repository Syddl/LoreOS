## Old vs new

| Behaviour | Before | After |
|---|---|---|
| Signup | 405 | Takes `pg_advisory_xact_lock(hashtext('loreos.signup'))`. 403 once any user exists. 422 for a password under 12 characters, for a `workspace_name` that is blank, over 100 characters or starts with `eval-`, and for a bad or long email. Otherwise the user becomes owner of the new workspace (default "My workspace") and of Default, gets a session, and the route returns 201 `Me` with the cookie. |
| Login | 405 | Calls `rate_limit` on `login:email:<normalised email>` (limit 5) and `login:ip:<client host>` (limit 20), 900 s window, before verifying. A refusal gets 429 with the larger `Retry-After` and no verification. Both failure cases get the same 401 body and stay counted. A success refunds both buckets after the `authenticate` session closes. |
| Logout | 405 | Uses `Depends(auth.current_user)`, so an `Authorization` header gets 403. Deletes the session row, clears the cookie, returns 204. |
| `GET /api/me` | 404 | 200 `Me`, or 401 |
| `Me.workspaces` | n/a | Excludes `eval-%` even with a membership, oldest workspace first: the same filter and order as `GET /api/workspaces` |
| Invite accept | 405 | One transaction. It marks the invite used and returns its workspace (no row gets 404). Logged in: adds the membership idempotently, 200. Logged out: 422 or 409 roll the invite back to unused; otherwise it creates the account and session, 201 with the cookie. |

**How the concurrent-guesses test works.** It sends 20 requests with `asyncio.gather` over an `httpx2.ASGITransport`. The spy replaces `auth._verify`. A request is counted either when it reaches the seam or when it is answered. One that reached the seam is only answered after the event is set, so no request is counted twice before then. The spy waits with `asyncio.wait_for(event.wait(), 5)`. The test asserts `calls <= 5` and exactly 5×401 plus 15×429.

**What the tests don't cover:**
- A real proxy setting the client IP (`FORWARDED_ALLOW_IPS`).
- A login that straddles a window boundary (ratelimit's own test covers it).
- Login timing parity beyond 2.2's one-verification test.

## Limitations

- **Signup now lands in Default.** Matching 4.3's order (oldest first, `created_at, name`) puts Default first, so `homeOf` after signup goes to Default rather than the new workspace. To change that, change both queries together.
- **Choices beyond the plan:**
  - **Email check:** at most 320 characters and an `x@y` pattern, on login, signup and accept. A huge email would otherwise become a rate-limit bucket key larger than a btree entry and give a 500. A malformed login email gets 422 and is not counted.
  - **Stale cookie on invite accept:** an unknown or stale cookie counts as logged out. The Invite screen shows the account form after `/api/me` returns 401, and still sends the old cookie with it.
  - **409 for a taken email:** comes from the unique violation (sqlstate `23505`) on insert, so it also holds under a race.
  - **Signup check order:** 422 checks run before the lock, so a short password gets 422 even when signup is closed.
- **Logout reads the cookie itself after `current_user`.** `current_user` returns the user, not the token, so to delete the right session row logout reads `request.cookies` only after `current_user` has refused any `Authorization` header and validated the session.
