**What I changed from the plan, and why:**
- **Repeated packages.** The plan says to walk `dependencies` "once per name and version". In the real `npm ls --json` output, a repeated package appears in full at one place and as a stub without `dependencies` elsewhere, and the stub often comes first. If the walk stops at an already-seen entry, it finds only 70 packages instead of 84, and the missed 14 are never checked. So `npm_packages` lists each name and version once but walks every node's children. The fixture's duplicate has its stub first, and red-proof 3 pins this.
- **Review row 14.** The first version of the subprocess test, with only a non-ASCII description, did not catch the bug: red-proof 2 survived. Python on Windows reads a text-mode stdin with `surrogateescape`, so a cp1252 read does not raise. It silently turns the text into garbled characters. That matters when it changes a verdict: `“GPL” v3` in curly quotes reads as `â€œGPLâ€`, the regex word boundary disappears, and the package would pass. The reject test now includes that package, and red-proof 2 goes red on it.

What the tests do not exercise:
- Whether an MPL-2.0 dependency is really unmodified.
- The real `npm ls` output; `check:licenses` covers that.
- The ANSI decoding on Linux, where stdin is UTF-8 in either mode.

## Limitations

- `--omit=dev` means frontend devDependencies, lightningcss among them, are never checked. That follows the plan.
- If a license string contains a character cp1252 cannot encode and the FAIL line is printed to a pipe on Windows, the line crashes with a `UnicodeEncodeError` traceback instead of printing. The exit code is still 1, so the check still fails.
- A repeated package's license is read from its first occurrence. In the current tree every stub carries `license` (434 of 434 entries).
- `claim-green` has not been run; the commits are not pushed.
