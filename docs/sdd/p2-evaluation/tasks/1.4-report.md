## Old vs new

| Behaviour | Before | After |
|---|---|---|
| Checking the corpus on disk | no code | `corpus_problems(manifest, corpus_dir)` returns one problem per file that is missing, has the wrong sha256 (over its raw bytes, through `ingest.sha256`), or resolves outside `corpus_dir`. Each problem names the file and the fix (`run npm run eval:fetch`, or fix the path in `eval/corpus.json`). |
| Downloading the corpus | no code | `fetch(manifest, corpus_dir)` skips each file that `corpus_problems` finds good. It refuses a path outside `corpus_dir` with no request. Otherwise it downloads with `urllib.request.urlopen(url, timeout=60)`. The bytes go to `<target>.part`, and are renamed onto the target with `os.replace` only after the sha256 matches. A mismatch deletes the `.part`. It prints one line per downloaded file and returns the problems. |
| A failing file | no code | An HTTP error names the file, the status and the URL. A network failure names the file, the reason and the URL. A hash mismatch names the file, the hash it got, the expected hash and the URL. Every case leaves nothing at the path, and the run keeps going, so one run reports every bad file. |
| `python -m loreos.evaluation.fetch` | no module | `main()` reads `dataset.read_manifest(dataset.MANIFEST)` and `dataset.CORPUS_DIR` at call time. It runs fetch and prints `<dir>: downloaded n, already present m, problems k`, then each problem to stderr. It returns 1 on any problem. The entry point calls `sys.stdout.reconfigure(errors="replace")`. |
| `git status` after a fetch | `eval/corpus/` would show as untracked | ignored |

## Limitations

- `main()` is untested and has never been run, because `loreos.evaluation.dataset` lands from task 1.1. The phase 3 check (`npm run eval:fetch` against the real hosts) proves it.
  - Its `from loreos.evaluation import dataset` sits inside the function only so this module imports without task 1.1's file. Once 1.1 lands, task 3.1 (owner of `main`) can hoist it to the top of the module. Reading `dataset.<NAME>` at call time holds either way.
- `main` hashes the corpus twice: once to count the files already present, and once inside `fetch`. That is under a second for 48 files.
  - The download count is `total - present - problems`. It relies on `fetch` adding at most one problem per file and skipping exactly the files `corpus_problems` passes. A later edit that breaks either rule would make the count wrong, and no test pins it.
- `corpus_problems` also refuses a path that resolves outside `corpus_dir`. This goes beyond the brief, which named only missing and changed files. With it, the preflight never reads a file outside the corpus, and `main`'s counts stay exact. Task 1.1's `manifest_problems` refuses `..` by spelling first.
- A 2xx status other than 200 is not refused by its status. Its body still has to match the sha256, so wrong bytes never land.
- An `http.client.IncompleteRead` (a truncated body) is not an `OSError`. It propagates and stops the run rather than being recorded as a problem.
- Each file is read whole into memory before hashing. The PDFs are a few MB each.
