## Old vs new

| Behaviour | Before | After |
|---|---|---|
| Evaluation workspace | none | `eval-` plus 12 hex of a sha256 over a JSON list of: the corpus hash; the source of `parsing.py`, `chunking.py` and `ingest.py` (CRLF read as LF); `CHUNK_TOKENS` and `CHUNK_OVERLAP`, read at call time; the embedding model; and `OPENAI_BASE_URL` (or `""`). `workspace_status` returns the oldest workspace with that name, and whether every corpus file's sha256 is `processed` in it. |
| Corpus ingest | none | The run finds or creates the workspace, then calls `ingest.ingest` on each file in its own `workspace_session`. A document that is not `processed` stops the run before any answer call. The error is `<file>: <status> after ingest (<stored error>); fix or replace the file, then run again`. A reused workspace re-embeds nothing, because ingest deduplicates by sha256. |
| Per question | none | Questions run in file order, or `questions[:limit]`. `retrieval.search` asks for k=10 and is timed with `perf_counter`, giving `search_ms` rounded to 0.1. The connection is opened before the timer starts. `answer_from_hits` then gets `hits[:answering.TOP_K]`. A non-refused answer is judged on only its cited passages, `dict(n, source, text)` under their original numbers. A row is appended only once it is complete. |
| Failure classes | none | An `openai.APIError` from answering or judging propagates. Any other exception from answering gives a refused row with `reason: "answer_error"`, text `REFUSAL`, no citations, `answer.error = "<Class>: <message>"` and a note. That covers a `LengthFinishReasonError`, which is an `OpenAIError` but not an `APIError`. A `VerdictError` gives `judge = {grade: null, rationale: null, error}` and a note. A refused row has `judge: null`. |
| Calibration | none | Unless `--limit` is set, each row of `dataset.CALIBRATION` is judged with its own question, answer and passages. Pairs are `{id, human, judge}`, with `judge: null` and a note on a `VerdictError`. A missing file, or a skip because of `--limit`, adds a note. |
| Result file | none | Exactly the spec's fields, in the spec's order. `git_sha` is the preflight's sha; `created_at` is UTC, `YYYY-MM-DDTHH:MM:SSZ`. `usage` is mapped from `llm.USAGE`, which is cleared at the start; a non-zero `responses_without_usage` adds a `usage:` note. `calibration_hash` is null when the calibration was not used (missing, or `--limit`). The file is named `<YYYYMMDDTHHMMSSZ>-<mode>-<sha8>.json` and written to a temp file in the same directory, then `os.replace`. It is UTF-8 JSON with LF endings, indent 2, `ensure_ascii=False` and a trailing newline. |
| Destination | none | The result goes to `results` only when every one of these holds: no limit; 60 to 100 questions; `calibration_rows == CALIBRATION_ROWS` with no calibration judge errors; judge agreement and faithfulness non-null; `tree_clean()` at the write; `git_sha()` equal to the preflight's sha at the write. Otherwise it goes to scratch, with one `scratch: <reason>; <fix>` note per unmet rule. |
| Stop mid-run | none | Any `BaseException` after the inputs are read writes the completed rows to scratch with `stopped: <Class>: <message>` in `notes`, prints the path on stderr, and re-raises. That includes an ingest failure, an `APIError`, `KeyboardInterrupt` and `CancelledError`. |
| Committed-result check | none | `result_problems(result)` names a `schema` other than 1, a `destination` other than `results`, or a null judge agreement, each with its fix. A test applies it to every real `eval/results/*.json`. |
| Mode | none | Only `vector`; any other raises `ValueError` before anything is read. |

What the tests cover, against the plan's acceptance list:

- **A full run.** 60 questions (15 unanswerable) and 30 graded calibration rows go to the patched results directory. The test pins:
  - the file name pattern, `{\n  "schema": 1,` with LF endings and a trailing newline, and UTF-8 `café` with no `\u` escape;
  - the exact key order, the settings, all three hashes and the workspace;
  - `notes == []`, every metric and latency non-null, the exact counts, faithfulness 1.0, agreement 20/30, the confusion matrix, and the calibration judge calls;
  - the row, hit and citation key order, string uuids, `relevant` for a heading hit and a page hit, and the citation `source` label.
- **Usage.** Stale `embedding_input=7` and `judge_input=999` are seeded. Fakes that bump `llm.USAGE` give exactly `embedding_tokens = 14 chunks + 3 questions`, answer 300/30 and judge 150/15, plus the `usage: 3 OpenAI responses` note.
- **Judge input.** Cited [2] and [4] reach the judge as exactly `[{n: 2, ...}, {n: 4, ...}]`, built from those hits.
- **Reuse.**
  - Before any run, the status is `(None, False)`.
  - A second run embeds only the 2 questions, reports `reused: true` and leaves one workspace with that name.
  - Deleting the PDF document makes the status `(id, False)`.
- **The workspace key.** It is `eval-` plus 12 hex and stable for the same inputs. Each of these changes the name: `CHUNK_TOKENS`, `CHUNK_OVERLAP`, `OPENAI_BASE_URL` set to another value, `OPENAI_BASE_URL` unset, `EMBEDDING_MODEL`, and a corpus sha256.
- **Same code path.** `fake_draft` receives the first 5 of the row's 10 hits, by chunk id.
- **Ingest failure.** `make_pdf([""])` added to the corpus raises `nist/blank.pdf: failed after ingest (parse: ParseError: no extractable text ...`. `fake_draft.calls` and `fake_judge.calls` stay empty, and a partial scratch file has no rows.
- **Destination.**
  - 59 and 101 questions use the real bounds.
  - Limit, missing calibration, a judge that always fails, 1 of 30 calibration verdicts failing, the tree dirtied mid-run and HEAD moved mid-run use a 4-question set with `MIN_QUESTIONS = MAX_QUESTIONS = 4` patched. The bounds are read at call time, and this keeps the file at about 30 s instead of 54 s. A control case shows the small set alone goes to results.
  - The tree and HEAD cases flip only after the first draft call, so a check made at the start of the run would miss them.
  - Each case lands in scratch with its `scratch:` note, and `result_problems` refuses it.
- **Failure classes.**
  - A `RuntimeError` and a `LengthFinishReasonError` from answering each give an `answer_error` row with its note, and the run continues.
  - A `VerdictError` on one row is recorded there and noted, and the next row is graded.
- **Partial results.** Four stops on the third question each re-raise the same object, leave one scratch file with exactly the first two rows and `stopped: <Class>: <message>` last in `notes`, and print the path on stderr. The four are an `APIConnectionError` from answering, the same from judging, `KeyboardInterrupt` and `CancelledError`.
- **Git helpers.** `git_sha()` returns 40 hex in the repo. In a fresh `git init` under `tmp_path`, the tree is clean, an excluded file keeps it clean, and an untracked file makes it dirty. `git_sha()` with no commit raises `git rev-parse HEAD failed ...`.

What these tests do NOT exercise:

- Real OpenAI calls: the llm functions are faked.
- Real git timing around the preflight: `git_sha` and `tree_clean` are patched in the run tests and exercised only against a temp repo.
- A failure while reading the inputs: that happens before the `try`, so it writes no partial file, and the preflight has validated them.
- The `.part` cleanup after a failed write.
- A `CHUNK_TOKENS` change actually changing the chunks: `chunking.chunk` binds its defaults at definition time, so only the key reacts.

## Limitations

- The run prints nothing while it works. A 100-question paid run takes minutes in silence; the partial file covers a Ctrl-C, but the operator sees no progress. Task 3.1's CLI cannot hook into the loop. A per-question line from `evaluate` would need a follow-up.
- Two results written in the same second with the same mode and sha get the same file name, and the second replaces the first. A real run takes minutes, so this happens only in tests, which read each result before the next run.
- A crash inside `_write` leaves a `*.part` file next to the target. In `eval/results/` that file is untracked, so the next preflight refuses the dirty tree until it is removed.
- `git_sha` and `tree_clean` run in `dataset.ROOT`, which is `EVAL_DIR.parent` by definition. `ROOT` is the root's single owner and the name a test patches.
- An answer-error row carries its error at `answer.error`, a key the row shape lists for no other row. `metrics.summarize` and task 3.2's draft read only `found`, `citations` and `judge`, so neither is affected.
- `npm run check:all` was not run; the main session runs it once for the phase.

- Each question opens its own database connection (`NullPool`), about 70 ms per question against the local testdb. The timer starts after the connection opens, so `search_ms` excludes it, but the run's wall time includes it. Owner: none for P2.
