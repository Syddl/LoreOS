## Old vs new

| Behaviour | Before | After |
|---|---|---|
| `## Title {#id}` | `["Title {#id}"]` | `["Title"]` |
| `## Collaboration{#collab}` (no space before the block) | `["Collaboration{#collab}"]` | `["Collaboration"]` |
| `## 🤝 Collaboration{#collaboration}` | `["🤝 Collaboration{#collaboration}"]` | `["🤝 Collaboration"]` |
| `#### Traveling with 1Password{#travel-mode}` | `["Traveling with 1Password{#travel-mode}"]` | `["Traveling with 1Password"]` |
| `## <i class="fas fa-tasks fa-fw color-orange font-awesome"></i>Compliance` | the tag kept in the title | `["Compliance"]` |
| `## Use {braces} here`, `## Ends in {braces}` | unchanged | unchanged (only a trailing `{#...}` is removed) |
| `## {#only-an-anchor}` | `["{#only-an-anchor}"]` | `[""]`, the same as an empty heading |
| `## Teams {#teams}` then `### <i class="fas fa-tasks"></i>Compliance` | `["Teams {#teams}", "<i class=\"fas fa-tasks\"></i>Compliance"]` | `["Teams", "Compliance"]` |
| `parse()` on `"## " + "{#" * 100_000` and `"## " + "<" * 200_000` | not affected before this task. The first version of the cleanup (`\{#[^}]*\}\s*$` and `<[^>]+>`) took 12.95 s and 25.62 s. | 0.01 s and 0.02 s |

The order is: drop tags, then drop a trailing `{#...}` block, then strip. Every Markdown upload goes through this; `.txt` and PDF sections have no heading path and are unaffected.

Why each step is linear:
- **Tags.** `<[^<>]+>` stops at the next `<`. Each character is scanned from at most one `<`, so a line of `<` costs one pass.
- **Anchor block.** The text is right-stripped. It counts as an anchor block when it ends in `}`, contains a `{#`, and no `}` falls between the last `{#` and the final `}`. Then it is cut at that `{#`. The whole check is one `rfind` and one `in`. This matches the old `\{#[^}]*\}\s*$` regex: an earlier `{#` could only match if the span after the last `{#` were free of `}` as well.

## Limitations

- Only documents uploaded after this change get clean paths. A document already ingested keeps its old `heading_path` rows until it is uploaded again. `ingest.py` puts the path in front of the embedded text, so a re-upload also changes those chunks' embeddings.
- `HTML_TAG` drops anything shaped like `<...>`, including a literal in the heading text: `` ## The `<div>` element `` becomes ``The `` element``, and `## a <b> c` becomes `a  c` with the inner double space kept. Both outputs were confirmed with a scratch script. The spec asks for every tag to go, and no corpus heading needs more than that. Collapsing inner whitespace or respecting code spans would need a further change.
- Unlike `<[^>]+>`, `<[^<>]+>` does not let a tag contain `<`. In `<a <b>`, only `<b>` is removed. A real tag never contains `<`.
- Other inline Markdown (`**bold**`, `[link](url)`, backticks) stays in the title, as before.

## Findings outside the owned files

- **`HEADING` is quadratic on a heading with a long interior run of spaces or tabs.** This affects `backend/loreos/parsing.py` and predates this task. It is in an owned file but out of this task's scope; the coordinator ruled that it be reported, not changed. `HEADING.match("## a" + " " * n + "b")` takes 0.92 s at n = 10k, 3.84 s at 20k and 16.4 s at 40k. That projects to several minutes for a 200k line, so one hostile upload can hold a worker. The cause is the lazy `(.*?)`: at every position it tries `[ \t]+#+` and `[ \t]*$`, and each attempt re-scans the rest of the space run. One fix:
  - match only `^ {0,3}(#{1,6})(?:[ \t]+(.*))?$`;
  - remove the closing `#` sequence in code: `rstrip(" \t")`, then strip trailing `#`s only when a space or tab precedes them, then `rstrip(" \t")` again;
  - add `"a" + " " * 200_000 + "b"` to `test_hostile_heading_parses_in_linear_time`.

  Suggested owner: a follow-up task on `parsing.py`, before P2 runs on uploads that are not trusted.
