## Old vs new

| Behaviour | Before | After |
|---|---|---|
| Relevance of a hit to a label | No code | `is_relevant(hit, source)`: same file, and the label's heading path is a list prefix of the hit's (`hit.heading_path[:len(p)] == p`), or the same page. An empty label path matches nothing. A hit is duck-typed (`retrieval.Hit`, `answering.Citation`, anything with `filename`, `heading_path`, `page`). `matched_sources` returns the indices of matching sources. |
| Corpus outline | No code | `outline(corpus)`: files in sorted order, one `OutlineEntry(file, heading_path, page, chunks)` per parsed section (two sections with the same path stay two entries), `chunks = len(chunking.chunk([section]))`, the same defaults ingest uses. |
| Label resolution | No code | `label_problems(questions, entries)`: for every source of every answerable question, an unknown file is one problem, and a label that covers no section is another, e.g. `q1: handbook.md: heading "Leave > Sik" matches no section in outline.txt; closest: "Leave > Sick"`. A heading label resolves when it is a list prefix of some entry's path in that file, so a heading with no text of its own (a parent of sub-headings) still resolves. A page label resolves when that page has a section. The closest match comes from `difflib.get_close_matches` over that file's `" > "`-joined paths. |
| Broad labels | No code | `broad_labels(questions, entries, max_chunks=3)`: one warning per source whose covered sections sum to more than `max_chunks` chunks, naming the question id, file, label and count. |
| `outline.txt` text | No code | `render_outline(entries)`: a header that shows how a line becomes a label (`{"file": "<file>", "heading_path": [...]}` with the path or any prefix of it, `{"file": "<file>", "page": n}` with the physical page), then `## <file>` and one line per entry: `Leave > Sick  (chunks: 1)`, `page 3  (chunks: 1)`, `(before the first heading)  (chunks: 1)`. Headings are printed exactly as the parser produced them. |

## Limitations

- `outline` passes `parsing.ParseError` and `UnsupportedType` straight through for a corpus file that does not parse. The callers (the preflight and `fetch.main` in 3.1) decide how to report it. Ingest would fail on the same file.
- A heading that itself contains `" > "` reads ambiguously in `outline.txt` and in the closest-match suggestion. Resolution compares lists, so it is unaffected. None of the chosen handbook pages is known to have one; the real outline from 3.3 would show it.
- Task 1.6 (heading cleanup) changes what `parsing.parse` returns. The outline reads the parser, so it follows automatically. The fixture corpus has no anchors or HTML, so this suite does not depend on 1.6.
